1. Document Overview
Project Name: StudentForge LMS
Document Version: 2.0 — supersedes v1.0. Adds full student-experience scope, a phased release plan built around a 4-day production sprint, non-functional requirements, and a data model overview.
Target Audience: Engineering, Product, Design, QA
Core Value Proposition: An integrated, real-time Learning Management System blending asynchronous course delivery with synchronous live classrooms, persistent messaging, calling, assessments, and a complete student engagement layer (progress, credentials, discovery, and support).
Build Context: This document is scoped in three phases. Phase 1 is the 4-day production sprint for a 4–8 person team and covers only what real students need on day one. Phases 2 and 3 extend the platform to full feature parity with this PRD. See Section 5 for the exact breakdown.
2. Product Objectives & Success Metrics
2.1 Objectives
Deliver a seamless dual-learning experience (self-paced Courses + real-time Live Classes) in a unified interface.
Provide low-latency, scalable real-time collaboration (chat, audio/video streaming, presence detection).
Maintain high data reliability and cross-region resilience for globally distributed learners.
Give students a complete learning loop — discover, enroll, learn, get assessed, get credentialed — without leaving the platform.
Ship a safe, tested Phase 1 MVP within 4 days without compromising security or payment integrity.

3. User Personas & Roles
3.1 Student
Goal: Learn a skill on their own schedule, get help when stuck, and walk away with proof of completion.
Frustrations with typical LMS tools: content locked behind clunky players, no offline access, doubts go unanswered, no sense of progress or motivation to continue.
Context of use: mixed devices (mobile-heavy for video, desktop for assignments), variable internet quality, time-constrained around work or school.
Core needs: fast discovery, frictionless enrollment/payment, reliable playback, live class access without setup pain, a place to ask doubts, visible progress, and a credential at the end.
Student Permissions
Browse & enroll in courses, manage wishlist
Watch VODs and join live sessions
1:1 / group chat and calls
Submit assignments, take quizzes, view grades and feedback
Manage own profile, payments, and notification preferences
3.2 Instructor
Goal: Create and deliver course content efficiently, run engaging live sessions, and grade fairly without administrative overhead.
Frustrations with typical LMS tools: slow content upload pipelines, no visibility into student engagement, moderation tools bolted on as an afterthought.
Core needs: simple content authoring/versioning, reliable scheduling, in-session moderation controls, a single place to grade and give feedback.
Instructor Permissions
Create & manage courses (draft, review, publish, version)
Schedule/host live classes
Grade assessments and give feedback
Moderate class chat and manage session participants
View per-course engagement analytics
3.3 Admin
Goal: Keep the platform compliant, financially accountable, and healthy at scale without manual firefighting.
Frustrations with typical LMS tools: analytics scattered across tools, unclear audit trails, manual role management.
Core needs: centralized user/role governance, platform-wide analytics, billing oversight, and compliance reporting.
Admin Permissions
User & role governance
Analytics & compliance reporting
Platform billing & settings
Content moderation escalation and audit log access

Note: Video strategy: Zoom Video SDK is used for both scheduled live classes and ad-hoc 1:1 tutoring calls. Raw WebRTC is intentionally out of scope — building and operating a separate signaling/TURN/STUN stack in parallel would consume days the 4-day sprint does not have, for no functional gain over what Zoom SDK already provides.
Note: Database: CockroachDB is confirmed as the platform database per team decision. Its distributed, multi-region design is the right long-term choice once the platform scales past a single region; in Phase 1 it is used in single-region mode to keep operational complexity low while preserving the migration-free path to multi-region later.
5. Release Plan & Phasing
This is the section that answers "what do we build first." Everything in Section 6 is tagged by phase. Do not start Phase 2 or 3 items during the 4-day sprint.
5.1 Phase 1 — Day 1 to Day 4 (Production MVP)
Goal: one core learning loop, fully working end-to-end, safe for real students and real payments.
Day-by-Day Breakdown (team of 4–8)
Day 0/1 — Lock scope and schema. Assign one module per pair: (a) Auth & user roles, (b) Course content & playback, (c) Live classes via Zoom SDK, (d) Chat & notifications, (e) Payments & enrollment. Scaffold with Antigravity agents in parallel where possible.
Day 2 — Build core CRUD and flows per module. Course upload/playback, live class scheduling/join, 1:1 and course chat, payment checkout. Agents handle boilerplate; humans review auth, payment, and data-access code line by line.
Day 3 — Integration. Wire modules together into one flow: enroll → watch/join live → chat → get graded on a simple quiz. This is where agent assistance helps least — plan for manual engineering time here.
Day 4 — Manual QA on the non-negotiables (below), fix blockers only, deploy. No new features on Day 4.
Phase 1 Non-Negotiables (cannot be cut, whatever else is descoped)
Role-scoped authentication and authorization (Student / Instructor / Admin)
HTTPS everywhere, no hardcoded secrets, basic input validation on all forms
A tested payment flow, including at least one failure-path test (declined card, timeout)
A privacy notice / consent flow before collecting any student data
Zoom SDK token generation and expiry handled correctly (no orphaned sessions)
Phase 1 Feature Scope
Async Courses: upload, hierarchical structure, playback with speed/auto-resume/progress tracking
Live Classes: scheduling, join flow, screen share, host moderation, cloud recording to S3
Communication: course chat, 1:1 chat, push notifications for class reminders
Payments: single payment method, checkout, invoice/receipt, basic refund path
Assessments: one quiz type (auto-graded, single attempt) — enough to close the learning loop
Student Dashboard: enrolled courses, continue-watching, upcoming live classes (minimum viable version)
Explicitly Deferred out of Phase 1
Gamification (streaks, badges, leaderboards)
Notes/bookmarks tied to video timestamp
Downloadable offline content
Certificates and LinkedIn sharing
Discussion forums, peer review, structured Q&A boards
Course search/filter/recommendation engine, ratings & reviews, wishlist
Multi-language/localization, dark mode
Parent/guardian view
Multiple payment methods, coupons, subscriptions/EMI
Plagiarism check, multiple quiz types, rubric-based grading

7. Non-Functional Requirements
7.1 Security
All traffic over HTTPS; secrets managed via environment/secret store, never hardcoded or committed
Role-based access control enforced server-side on every endpoint, not just hidden in the UI
Input validation and sanitization on all user-submitted content (forms, chat, file uploads)
Any AI-agent-generated code touching auth, payments, or data access is reviewed by a human before merge, given documented prompt-injection risks in agentic coding tools
7.2 Privacy & Compliance
Privacy notice and consent flow before collecting student data — required even for Phase 1
Formal FERPA / GDPR / COPPA review scheduled for Phase 3, sooner if any student is confirmed to be a minor
Data retention and deletion policy defined before Phase 2 launch
7.3 Accessibility
Captions and transcripts for recorded content  [Phase 2]
WCAG 2.1 AA audit and remediation  [Phase 3]
Multi-language UI and subtitles  [Phase 3]
7.4 Performance & Scalability
Chat delivery latency under 150 ms globally (see KPIs)
Live class session drop rate under 0.5%
API and database uptime of 99.95%
Single-region CockroachDB for Phase 1; multi-region rollout planned for Phase 2 once user base is cross-region
7.5 Reliability & Recovery
Automated database backups from Day 1 of Phase 1, not deferred
Documented incident response path for payment or video-infra failures during live sessions
